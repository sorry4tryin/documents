- a viable approach to spawning multiple child agents in coordination with a parent_agent to complete tasks effectively and efficiently. each child is specialized in a random primary skill to finish the task with max efficiency to not exceed the dedicated context window–no agent will have similar primary skills; this setup is used to suspend human attention by all means especially for the parent agent. for example, instead of the user prompting the parent_agent to spawn fifty child_agents that have a high probability to create disruptions,  the prompt the user inputs (with or without the term agents) will automatically prompt the parent_agent to prompt the child_agent–the child_agent can reciprocate a prompt to the parent_agent but it is less likely.
	- platform: opencode––migrate to `pi.dev` (TBA)
	- structure:
		- session_name: a seven word statement that provides concise understanding on what the session is anticipated to perform or what the session has proved to display
		- parent_agent: the operator AI assistant that handles the foundational aspects of a session: delegating, verifying, and enforcing. when the user_prompt is identified the parent_agent will start by analyzing a short description over what the user is prompting. this description should include a  two to three sentence statement with concise diction for easy readability.  the parent_agent completes analyzation and starts by delegating the task to a specific number of child_agent from the results. each child_agent is carefully monitored; make sure it follows a set document of rules and regulations that invoke effectiveness and efficiency.
		- child_agent: a specialized AI assistant that handles a specific type of task. initially when the parent_agent encounters a task that matches a child_agent's description it will spawn that agent into the active session. when the response of a user_prompt consist of a side task that would interrupt the main conversation with search results, logs, or file contents, complete the task independently to not affect the context of the parent_agent–must return a report in the summary.
			- report: in the summary section of the parent_agent last response, the parent_agent will receive a line of text from the child_agent prior to the child_agent closing. the line is identified to be a report, which follows the framework `[[instance_number]child_agent]: [a summarized report of what occurred in this child_agent instance].` each child_agent is marked with a instance_number to enable precise spawning with the help of LLM memory–this will in turn provide a smooth workflow for repetitive task. when  a child_agent is ready to close it is required to print out a summarized overview following these main components: a response must contain two to five sentences summarizing the information in context and the deliverable requested, but it must contain a multi-step trace depiction of what is being considered, what subtasks were announced, and what tool calls were made with their integrated outputs. although this is evident, an exception is granted for simple or conversational prompts.  answers must always be made, with a final response  containing all fully read sources while integrating tool outputs. after this part of the response is completed a one to three sentence is required to display what the user and agent learned and how improvements can be made.
		- boundaries: the parent_agent is allowed to spawn child agents to its own discretion without exceeding the 50 instance limit. the purpose of apply a 50 instance limit is to prevent any performance loss, maintain each agents context window, and to present a functional workflow. to prevent any performance loss, we must implement a system allowing our ai agent (opencode/pi.dev) to send a tui notification prompting a warning at the exact time a child_agent except the build-in ones, exceeds 15000 tokens. moreover it would be optimal to provide a short tui interface that displays the statistics of each child_agent. this will include the following: token_count, model_name, task_name (depends if there is a todo list), session_name, runtime, and agent_group. 
			- token_count: displays the amount of tokens currently used for that specific child_agent
			- model_name: identifies the model and provider (normally 'provider/model_name') 
			- task_name: when a todo list is created, the name of the task set for the child_agent belongs here
			- runtime: in the format 'hour:minute:secs', this will display the duration the child_agent has been active for currently; it will be a live count aswell. when the child_agent is closed, the font color will be red or display a certain icon to provide clear indication that the agent is closed. moreover, when a agent closes the live count will discontinue and present the last log time active. 
		- compatibility score system: in the configuration a child agent, each agent belongs to a certain class. this class is identified to contain a variety of agents that include similar or opposite primary skills (the main function of an agent). class is defined through combination (capability testing with opposite primary skills) and specification (associate a set of children with a general task).
				- agent_group: a group of agents that all have different primary skills that when combined it is categorized as something complementary. an example, is described when  one agent is subjected to perform greatly in math, but will display high complementary with an agent that performs greatly in work ethics. the key point isn't that they have opposite primary skills, its that when both agents are applied in a certain field (task), effectiveness and efficiency are depicted. keep in mind that agent are not suppose to have complete similarities–in terms of primary skills–with other agents; thats why we have specialized workers.
